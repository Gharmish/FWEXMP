## 1. Executive summary

The codebase is in good mechanical health — typecheck, lint, 2,261 unit tests, CI and the production error log are all clean — and the nightly routines have already filed issues (and green fix PRs) for most of the defects a code read turns up. What needs fixing now falls into three groups:

1. **Operations, not code (the big ones).** All eight live listings have no open dates, so the marketplace cannot sell anything; host payouts have never been run (26 completed, paid bookings owed, two verified hosts have no IBAN on file); and two WhatsApp support threads have waited 22–23 days in "human" state. These are owner actions, and they outrank every code finding below.
2. **An owner-review backlog that already contains the fixes.** 25 routine PRs are mergeable with green CI, including the fix for the one open **P0** (issue #120: a stranger who knows a guest's phone can redirect that guest's booking emails and their signed `?k=` links). This scan independently confirmed #120 and 37 other open issues; merging the queue closes them.
3. **New defects this scan found (63 not yet tracked: 0 P0, 1 P1, 9 P2, 53 P3).** The most important new ones:
   - **SECURITY-03 (P1, reproduced live):** Supabase answers a wrong OTP with HTTP 403 `otp_expired`, but the sign-in action only counts 401/410 as a wrong code. The app-level brute-force throttle therefore never records a failure, and every guest who mistypes a code is shown the generic "server error" instead of "invalid code". Supabase's own per-IP verify limit is the only remaining defence.
   - **BOOKING-02 (P2):** every booking email and the confirmed / invoice / pay pages read the listing through the live-only `getExperienceBySlug`, so the moment a listing is paused or sent back to review, its existing bookings lose title, meeting point and map link.
   - **BOOKING-01 (P2):** rescheduling never recomputes the approval or payment deadline, so a request moved to an earlier date keeps a deadline that can sit past the new slot's start.
   - **ADMIN-HOST-01 (P2):** the admin experience editor writes `status` straight from the form, bypassing the readiness and approve gates the moderation flow enforces.
   - **MONEY-01 / MONEY-02 (P2):** a dispute refund on the default bank-transfer rail is queued with no payee and the guest is never asked for an IBAN; and payouts can be marked paid for bookings with an open dispute, leaving a later refund recoverable only by clawback.
   - **HYGIENE-01 / HYGIENE-02 (P2):** `main` has no branch protection while every push to it deploys production, and the config check misses the variables whose absence silently switches off payments, WhatsApp, phone sign-in and the signed booking cookie.

Overall grade: **B+**. The product is well-guarded where money moves and the routines are doing their job; the gaps are mostly state-machine edges, copy that no longer matches the refund rail, and process guards around deployment.

### P1

#### SECURITY-03 — verifyOtp only treats HTTP 401/410 as a wrong code — Supabase answers 403 otp_expired, so the brute-force counter never increments and guests see a generic error

`P1` · confidence medium · auth · `features/auth/actions.ts:413` · test gap

**Evidence.** actions.ts:413-417 `const message = error?.status === 410 || error?.status === 401 ? 'invalid_code' : 'server'; if (message === 'invalid_code') { await recordOtpVerifyFailure(phone, …) }` (email branch identical at :330-334). No check of `error.code`. actions.test.ts:182 mocks only `{ status: 401 }`. Current supabase/auth (auth-js 2.106.1 in node_modules/.pnpm) returns `403 Forbidden` with `error_code: otp_expired` ('Token has expired or is invalid') for both a wrong and an expired code; the 401 form is the pre-error-code GoTrue response.

**Scenario.** A guest mistypes the WhatsApp code: the action returns `message: 'server'` with no `fields.code`, so the form shows a server-error banner instead of 'wrong code', and `auth_throttle_events` gets no `verify_failed` row — `otpVerifyAllowed` (10 fails / 15 min) can never trip, leaving Supabase's project-wide rate limit as the only ceiling on code guessing. Verify by typing one wrong code on prod (or in Supabase auth logs: status 403, error_code otp_expired).

**Fix.** Classify by code as well as status: `error.code === 'otp_expired' || [401,403,410].includes(error.status)` → 'invalid_code' (and record the failure); keep 429 → rate_limited; add a 403/otp_expired case to actions.test.ts.

**Verification.** confirmed live — POST /auth/v1/verify with a bogus code returns HTTP 403 otp_expired; features/auth/actions.ts:331 and :413 only count 401/410 — both the phone and the email branch.

#### BOOKING-01 — Reschedule never recomputes approvalDeadline / paymentDeadline, so moving a request to an earlier date leaves its deadline past the new slot's start

`P2` · confidence high · state-machine · `features/bookings/lib/reschedule-core.ts:170` · test gap

**Evidence.** reschedule-core.ts:168-181 `.set({ date: newDate, startTime: experience.startTime, rescheduledAt, rescheduledFromDate, rescheduleCount, reminderSentAt: null, finalReminderSentAt: null })` — neither approvalDeadline nor paymentDeadline is touched. policy.ts:173 `const live = input.status === 'pending' || input.status === 'confirmed'` and rescheduleOption() (policy.ts:243-255) never reads paymentStatus, so pending requests and approved-but-unpaid holds are reschedulable; booking-manage-sections.tsx:277 renders the calendar whenever `rescheduleView && !isHoldLapsed` (isHoldLapsed is false for a pending row, confirmation-view.ts:93-98). The deadlines were clamped to the ORIGINAL slot at insert.ts:149-157 and transition-executor.ts:214-224.

**Scenario.** Request created 20:00 for a date 10 days out → approvalDeadline = tomorrow 20:00. At 21:00 the guest reschedules the pending request to tomorrow 09:00 (12h ahead, passes the 2h cutoff). approvalDeadline stays tomorrow 20:00, 11h AFTER the new start: the host can no longer approve (`too_late` from 07:00), the pending row keeps occupying the seat via holdStillCounts() until 20:00, and the expire cron then emails the guest 'your request expired' 11 hours after the experience ran. Same shape for an approved-unpaid request: paymentDeadline stays past the new start, so the page/email promise 'pay by 20:00' while createCheckout answers `expired` from 09:00. Moving LATER keeps the old slot's clamp, silently shortening the host SLA / pay window. A pending request whose approvalDeadline already lapsed (cron not yet run) can also be 'moved' and is expired a minute later.

**Fix.** In the reschedule UPDATE recompute the deadlines for the new slot: for `pending`, approvalDeadline = min(existing, slotCloseInstantMs(newDate, startTime, cutoff\*60)) and refuse (`wrong_state`) when the existing deadline has already lapsed; for `confirmed` + unpaid with a paymentDeadline, paymentDeadline = min(existing, slotCloseInstantMs(newDate, startTime, 0)) and refuse (`date_unavailable`) when the remaining window would be under MIN_PAYMENT_WINDOW_MS. Add a reschedule-core.test.ts covering both.

**Verification.** confirmed — reschedule-core.ts UPDATE sets date/startTime only; deadlines are only ever written by transition-executor.ts and request/insert.ts.
