## 1. Executive summary

Gharmish is a well-engineered codebase for a team of its size, and in several areas — the money core, the authorization model, the bilingual/RTL layer, design-system discipline — it is stronger than most launch-stage marketplaces. Every dimension graded B or better except dependencies (C), and the code carries its own decision history in comments, which is rare and valuable.

The audit found **one P0**: production runs Next.js 16.2.12, which carries two critical advisories including an unauthenticated remote-code-execution bug in the Image Optimization API triggered by AVIF — a format this app explicitly enables and accepts from host uploads. CI's own `pnpm audit` gate has been red because of it, which means the whole pipeline behind that step has been masked.

The **P1s cluster in four themes**:

1. **Release process.** Two P0 fixes from the August ops audit — the event-clock guard that stops a host approving, or a guest paying for, an experience that has already started, and the cron watchdog — have sat uncommitted in the shared checkout for five weeks while their UI copy, i18n keys and helpers were committed and deployed around them. Production therefore runs without them, and CI is not a gate for the manual `vercel deploy --prod`.
2. **Schema provenance.** The Drizzle migration history stopped on 2026-08-02; eight tables (including `user_roles`, `admin_totp_factors`, `cancellation_policies`) exist only in ad-hoc SQL or prose, so the repository can no longer reproduce production. Meanwhile `pnpm db:seed` deletes the live `moments`/`experiences`/`hosts` tables with no environment guard, and `.env` in this checkout points at the live pooler.
3. **Silent correctness gaps.** Referral attribution has been dropped on every booking since 2026-08-15 (the form posts `referralCode`, the action never parses it). A second WhatsApp message arriving during an agent turn is lost and never swept. A host or admin can change a live listing's start time or operating weekdays with confirmed bookings on it and nobody — guest, host, or admin — is told. Any unauthenticated POST to the HyperPay webhook fires a paid email + WhatsApp admin alert. And the server-side TikTok purchase conversion fires with the stored click id for every paid booking regardless of the guest's cookie choice, while the banner promises ad measurement only with consent.
4. **Test shape.** 33 of 39 server-action files have no tests, including `createCheckout` (the one action that opens a charge, and a file that has already drifted once) and every admin money action; Playwright never touches the database.

The **structural debt is boundaries, not conventions**: 14 two-way import pairs between feature folders, `lib/` acting as a second features layer (the support agent, conversations, marketing all write to the DB from `lib/`), features importing React components out of `app/` route folders, and four route files of 1,100–1,600 lines — none of it enforced by lint, so every one of these regressed after being fixed once. The single highest-leverage engineering investment is a lint-enforced boundary rule plus unused-export detection in CI.

**Overall grade: B.** Ship the P0 today, land the orphaned P0 fixes this week, then spend the quarter on schema provenance, the test pyramid's middle tier, and cron/boundary decomposition.

### What is genuinely good

- **Money model.** Whole-SAR integers computed server-side, commission/policy/VAT snapshots on each booking, an idempotent settlement arbiter (conditional UPDATE re-asserting the amounts it compared), append-only ledgers with CHECK constraints, capacity under `SELECT … FOR UPDATE`, wallet debits under a per-guest advisory lock, and a cron sweep behind every known crash window. No P0/P1 money defect was found.
- **Authorization.** One admin gate (`requireAdminActor`) that combines the `user_roles` lookup with an in-app TOTP second factor on every write — and a structural test that fails the build if any admin action bypasses it. Booking access is one greppable model (owner / signed cookie / pay-only link token). All three webhooks verify authenticity with constant-time compares; no secret is in the tree.
- **Bilingual and RTL.** Zero physical directional utilities in 642 files, 66 directional icons all mirrored, 3,457 keys in exact EN/AR parity, Latin digits pinned at every `Intl` call site, CLDR six-form Arabic plurals, and accessibility enforced by types (IconButton requires `aria-label`, never below 44 px).
- **Design system.** No 700/800 weights anywhere, no off-palette hex in product UI, one shadow token used only on floating layers, one `SPRING` constant behind every Framer transition, reduced motion honoured three ways.
- **Resilience under DB trouble.** Every public read is deadline-bounded with a pool reset on timeout, analytics writes run post-response on an isolated one-connection pool, public pages degrade to sample data, and the home page streams everything below the hero.
- **Conventions hold.** All 40 action files open with `'use server'`, validate with a shared zod schema, return a discriminated failure and never throw to the client; one component per file with named exports holds across 260 TSX files; incident history is written into the code next to the guard it motivated.
- **Tests are deep where they exist.** The settle test walks the Drizzle SQL tree to assert the exact WHERE columns of the race guard; 1,530 tests run in 2.3 s; CI runs typecheck, lint, audit, tests, build and e2e on every push.

## 3. Architecture & structure

**The intended layering is real on the happy path.** Pages import from `features/` 440 times and from `db/schema` only twice (both in cron/export routes); `features/` owns queries, actions, schemas and components consistently across 22 folders; formatting and money helpers are centralised (`lib/format.ts`, `components/ui/price.tsx`); auth is one chokepoint. Where it breaks is at the boundaries.

**Dependency picture (import counts).** app→features 440 · app→lib 403 · app→components 237 · features→features 599 · features→lib 590 · features→db 110 · **lib→features 20** · **components→features 6** · **features→app 3**. The last three are inversions.

| Signal | Value | Where |
|---|---|---|
| Two-way import pairs between feature folders | **14** | auth↔admin, bookings↔payments, bookings↔wallet, account↔bookings, admin↔host-experiences, admin↔wallet, admin↔host-applications, admin↔experiences, bookings↔experiences, bookings↔host-applications, experiences↔hosts, experiences↔reviews, experiences↔wishlist, promo-codes↔wallet |

| Feature importing from `app/` route folders | 3 imports | `features/host-bookings/components/booking-row.tsx:16-17`, `booking-copy.ts:2` |
| `lib/` modules that write to the DB or import feature internals | support-agent (1,617 lines), conversations (535), marketing, cancellation-policy, platform-settings | a second features layer living in lib |
| Files over 1,000 lines | 9 | `db/schema.ts` 2,404 · `booking-email.ts` 2,092 · confirmation page 1,611 · `booking-request-form.tsx` 1,273 · `admin/page.tsx` 1,203 · detail page 1,175 · `release-holds/route.ts` 1,130 · `experience-form.tsx` 1,091 · `payment-details-form.tsx` 1,039 |
| Longest single function | `requestBooking` — 641 lines (`features/bookings/actions.ts:288-929`) | validates, resolves identity, throttles, reserves, persists, sets cookies, fans out |
| Riyadh date/time helpers | 3 copies of `todayInRiyadh`, 2 of `addDays`, 4 “date + HH:MM → instant” builders | agree today only because KSA has no DST |
| Features lacking a root `types.ts` | 10 of 22 | convention in CLAUDE.md, unenforced |

**Verdict.** The shape is right and the conventions are strong; the boundaries are unenforced. A second reviewer confirmed the 14 folder-level cycles but found *zero file-level runtime cycles*, so this is coupling that blocks ownership and safe refactoring rather than a runtime hazard — a P2 structural theme, not a P1. Three moves fix most of it: (1) `eslint-plugin-boundaries` + `import/no-cycle` + `knip` in the existing lint job to freeze the graph; (2) an explicit public surface per feature (`features/bookings/public.ts`, `features/experiences/…`) with deep imports forbidden; (3) promote `lib/support-agent`, `lib/conversations`, `lib/marketing` to `features/`, and decompose the four god files behind pure, unit-tested view-models and a sweep registry.

### 4.1 P0 — fix today

#### DEPS-01 · Production Next.js 16.2.12 carries two CRITICAL advisories (AVIF Image-Optimization RCE) and CI's audit gate is red

`package.json:65` — *verified by lead* — confidence 0.92

```
"next": "16.2.12",  — `pnpm audit --prod`: critical "Next.js: Unauthenticated Remote Code Execution in Image Optimization API when AVIF files are used", vulnerable >=16.0.0 <16.3.3; `pnpm audit --prod --audit-level=high` exits 1
```

**Why it matters.** The vulnerable feature is enabled in this app: next.config.ts:98 sets `formats: ['image/avif', 'image/webp']`, `remotePatterns` allows the public `photos`/`avatars` Supabase buckets, and the host photo validator accepts AVIF uploads (features/host-experiences/lib/photo.ts:26 `'image/avif': 'avif'`), so an AVIF planted by any host account (or a compromised bucket object) reaches the optimizer. Independently, CI's `pnpm audit --prod --audit-level=high` step (ci.yml:26) fails today, so the main-branch pipeline is red and every other gate behind it (test, build, e2e) is masked.

**Fix.** Bump `next` to >=16.3.3 (16.3.4 is current) and `eslint-config-next` to the same version in one change, run `pnpm install`, `pnpm typecheck && pnpm lint && pnpm test && pnpm build`, then deploy from a clean export per the shared-checkout rules. As a stop-gap until deployed, drop `'image/avif'` from `ACCEPTED` in photo.ts. Verify `pnpm audit --prod --audit-level=high` exits 0 before merging.

### 4.2 P1 — fix this week

#### DATA-01 · Drizzle migration history is no longer authoritative — 8 tables and 11 bookings columns exist only in ad-hoc SQL or markdown

`db/migrations/meta/_journal.json:189` — *verified by lead; also reported as DEPS-03* — confidence 0.90

```
Last journal entry is idx 31 / 0031_magical_norman_osborn (2026-08-02); 0031 says "the 0031 meta snapshot now matches the real schema, so future generates diff cleanly". Diffing db/schema.ts against 0031_snapshot.json: tables missing from the snapshot = admin_alerts, admin_totp_factors, cancellation_policies, conversation_messages, conversations, support_ticket_events, support_tickets, user_roles; bookings columns missing = checkout_integrity, fbclid, gclid, guest_note, marketing_consent, referral_code, refund_bank_*, ttclid.
```

**Why it matters.** The DDL for these lives in 19 hand-written supabase/*.sql files applied via MCP, and for user_roles / admin_totp_factors only inside docs/security/*.md. The 'enable RLS on all tables' step is recorded nowhere in the repo (memory: supabase-project.md). Consequences: a fresh environment (preview DB, Supabase branch, disaster recovery) cannot be built from the repository; `pnpm db:generate` will emit a huge catch-up diff that includes drops it infers wrongly; `pnpm db:push` remains a destructive interactive tool (memory: drizzle-push-drift). Every further ad-hoc change widens the gap.

**Fix.** Regenerate a single catch-up migration (0032) from the current schema.ts, verify it against the live schema (drizzle-kit pull into a scratch dir and diff), mark it applied in drizzle.__drizzle_migrations, and fold the RLS-enable statements plus user_roles/admin_totp_factors DDL into it so the repo is reproducible. Then make the rule mechanical: every future schema change ships as db:generate output applied via MCP, and add a CI step that fails when `drizzle-kit generate` against the committed snapshot produces a non-empty diff.

#### DATA-02 · db/seed.ts deletes hosts/experiences/moments with no environment guard against the live database

`db/seed.ts:17` — *verified by lead* — confidence 0.75

```
await db.delete(moments);
  await db.delete(experiences);
  await db.delete(hosts);
```

**Why it matters.** In this project the working checkout's DATABASE_URL points at the live gharmish-experiences database (memory: 'never flip vat_enabled in the shared live DB for testing'), and several sessions share the checkout. `pnpm db:seed` is listed as a normal project command in CLAUDE.md. The three deletes are not in a transaction: `delete(moments)` commits before `delete(experiences)` fails on the bookings FK RESTRICT, so a single accidental run wipes every live itinerary (moments) and, for experiences with no bookings yet, the listing and its host row. The only thing currently protecting production content is an incidental FK error on the second statement.

**Fix.** Refuse to run unless an explicit `SEED_ALLOW_DESTRUCTIVE=1` (or a hostname allowlist for local/branch DBs) is set, wrap the clear-and-insert in one transaction, and prefer upserts on slug (onConflictDoUpdate) so the script is idempotent without deleting. Consider removing `db:seed` from the shared checkout's package scripts or renaming it to make the destructive intent obvious.

#### AI-01 · A second WhatsApp message arriving during an agent turn is dropped and never swept

`lib/support-agent/agent.ts:28` — *verified by lead* — confidence 0.85

```
/** A second message arriving mid-run is picked up by the re-check at the end of this run. */
...
if (locked.length === 0) return { outcome: 'skipped' };
```

**Why it matters.** There is no re-check at the end of the run (grep for 're-check' finds only this comment). While the 90s lock is held, the webhook's after() leg for the next inbound message returns 'skipped' (agent.ts:272). The first turn was built from history loaded before that message, so it is not answered; then the reply sets lastOutboundAt > lastInboundAt, and sweepPendingAgentTurns skips the conversation (agent.ts:362: `if (lastOutboundAt >= inbound) continue`) and also requires the newest message to be direction 'in' (agent.ts:368), which it no longer is. WhatsApp users routinely send 2-4 short messages in a burst ('hi' / 'my booking' / 'GH-XXXX'), so this hits real guests daily and looks to them like the bot ignored their actual question until they write again.

**Fix.** After sending the reply in runAgentTurn, re-query for inbound messages newer than the turn's last history message (or compare conversations.lastInboundAt to the snapshot taken at lock time) and loop once more while the lock is still held; alternatively make the sweep condition 'last message is inbound OR any inbound exists after the last agent reply'. Add a unit test that a message inserted between loadThread and sendConversationReply gets a second turn.

#### ACTIONS-01 · requestBooking never reads `referralCode` from the form — referral attribution silently dropped on every booking

`features/bookings/actions.ts:292` — *verified by lead* — confidence 0.90

```
safeParse input lists utmSource/utmMedium/utmCampaign/gclid/ttclid/fbclid/marketingConsent/guestNote but no referralCode (lines 292-311); later `referralCode: input.referralCode ?? null,` (line 754). The client sets it: `if (utm.ref) formData.set('referralCode', utm.ref);` (booking-request-form.tsx:333) and the schema declares `referralCode: clickId` (schemas.ts:104).
```

**Why it matters.** zod strips keys absent from the parse input, so `input.referralCode` is always undefined and every booking since a0a7b02 (2026-08-15) is stamped `referralCode: null`. `grantReferralRewards` in lib/marketing/referral.ts keys off this column at settlement, so when the owner sets `referral_reward_sar` no reward will ever fire, and the attribution data for the dormant period is already lost. None of the 27 requestBooking tests cover it.

**Fix.** Add `referralCode: formValue(formData, 'referralCode'),` to the safeParse input and a test asserting a posted `referralCode` lands on the inserted row. Consider deriving the parse input from a single FIELD list shared with the client so a hidden field cannot be added on one side only.

#### TEST-01 · CI is not a release gate: production deploys bypass the green-build check

`.github/workflows/ci.yml:9` — *verified by lead* — confidence 0.70

```
on:
  push:
    branches: [main]
```

**Why it matters.** CI runs on push/PR, but production is shipped by hand (`vercel deploy --prod` from a git-archive export per CLAUDE.md 'Shared checkout' and the deploy-provenance memory), and the only local gate is a husky pre-commit hook that `--no-verify` skips. Add `needs: checks` to the e2e job so a broken unit suite fails fast.

#### OPS-02 · Any unauthenticated POST to the HyperPay webhook fires a paid admin alert (email + WhatsApp) — alert-flood DoS

`app/api/webhooks/hyperpay/route.ts:47` — *verified by lead* — confidence 0.85

```
} catch (error) {
  reportError(error, { surface: 'hyperpay-webhook:decrypt' });
  await notifyAdmin('settle_anomaly', { source: 'hyperpay-webhook', problem: 'notification failed decryption …' });
```

**Why it matters.** decryptOppwaNotification throws on any body whose GCM tag does not verify, i.e. on arbitrary attacker input. Each such request inserts an admin_alerts row, sends a Resend email and a Twilio WhatsApp template (dedupeKey is `admin_alert:<new row id>`, so nothing dedupes across requests). ## Appendix A — per-dimension assessments and strengths

### ARCH — Architecture & module structure (grade B)

Dependency picture (import counts, @/ paths): app→features 440, app→lib 403, app→components 237, features→features 599, features→lib 590, features→db 110, lib→features 20, components→features 6, features→app 3, app→db 2. The intended layering (app is thin; features own queries/actions/components; lib and components are leaves) is genuinely realised on the happy path: pages almost never touch Drizzle (2 imports, both cron/export), named exports and one-component-per-file hold with a single justified exception, formatting/money helpers are centralised in lib/format.ts + Price, and 91 co-located unit-test files pin the money paths. Where it breaks is at the boundaries: the feature graph has 14 two-way cycles (auth↔admin, bookings↔payments, bookings↔wallet, account↔bookings, admin↔host-experiences, experiences↔hosts/reviews/wishlist…), features/admin acts as a hub importing eight other features, lib/ has become a second features layer (support-agent, conversations, marketing, cancellation-policy all reach into features/bookings and features/wallet), and one feature imports React components out of an app/ route folder. Four route files carry 1,100–1,600 lines of orchestration (a 19-pass cron handler spanning eight domains, a 1,480-line single-component confirmation page), one server action is 641 lines, and the Riyadh date primitives exist in three copies. Conventions are strong; boundaries are unenforced. For a 20-engineer team this is a low B: the shape is right, but without a lint-enforced boundary rule and a decomposition of the four god files, ownership per team cannot be assigned and any change to bookings ripples through admin, wallet, payments, support-agent and cron at once.

**Strengths noted by the reviewer:**

- Feature-folder architecture is real, not aspirational: 376 files across 22 feature folders with queries.ts/actions.ts/schemas.ts/components/lib consistently present; app/ pages import from features 440 times and from db/schema only twice (cron + export routes).
- Component conventions hold almost perfectly: exactly one default export outside Next route files (lib/request.ts, required by next-intl), and only components/ui/motion.tsx bundles more than one exported component (a deliberate primitives module).
- Money and number formatting is centralised (lib/format.ts formatSAR/formatDate/formatTime, components/ui/price.tsx); no hand-rolled `SAR ${x}` strings outside the CSV export and the WhatsApp renderer, which has its own documented style.
- Test discipline is co-located and structural: 67 test files under features/, 24 under lib/, 1,530 passing tests, including tests that pin invariants (requireAdminActor on admin writes, transition-executor, payout-sql).
- The cron heartbeat is defensively engineered even though it is oversized: every pass is wrapped in its own try/catch (20 try blocks), capped per run (RECONCILE_LIMIT, REMINDER_LIMIT, COMPLETION_LIMIT), idempotent by state+dedupe flags, and watched by a deliberately separate watchdog route.
- Auth is a single chokepoint: features/auth/queries.ts getCurrentUser (react cache) and features/admin/guard.ts requireAdminActor are reused by wallet, admin, support and host surfaces instead of re-implementing session reads.
- Module docstrings carry decision history and rationale (lib/cancellation-policy.ts, release-holds header, watchdog header) — a new engineer can learn why a guard exists without git archaeology.
- Public-path DB reads are uniformly hang-bounded through lib/deadline.ts boundedQuery/withDeadline (15 layers use it), and fan-out is consciously waved to fit the pool size.

**Development areas proposed by this reviewer** (folded into §6):

- *Lint-enforced module boundaries (features↔features, lib→features, *→app) and unused-export detection in CI* — Every structural finding above (ARCH-02, 03, 05, 08, 12) regressed because nothing fails the build when a boundary is crossed. eslint-plugin-boundaries + import/no-cycle + knip, run in the existing GitHub Actions lint job, would freeze the current graph and let the team ratchet it down. This is the highest-leverage architecture investment available and needs no product time. (S/high)
- *Scheduled-work framework: sweep registry with per-pass run ledger and metrics* — The platform's critical background work is 19 passes in one route (ARCH-01) observed only by a staleness stamp. A registry of sweeps each recording start/end/counts/errors to a `cron_runs` table would give the admin dashboard a per-pass health view, allow per-pass alert thresholds, and make adding a domain sweep a one-file change owned by that domain's team. (M/high)
- *Split db/schema.ts (2,404 lines, 34 tables, 33 enums) into per-domain schema files with a barrel* — A single schema file is the most contended file in a shared checkout (the memory notes already document staging-collision pain on db/schema.ts). Drizzle supports multi-file schemas via a glob in drizzle.config; splitting into db/schema/{bookings,payments,wallet,hosts,experiences,support,admin}.ts with `db/schema/index.ts` re-exporting keeps every `@/db/schema` import working. (M/medium)
- *End-to-end coverage of the money paths (Playwright is 3 specs / 63 lines)* — 1,530 unit tests are strong, but the booking→pay→confirm→cancel→refund journey — the code most affected by the god files in ARCH-06/07 — has no browser-level regression test in CI. The scratchpad Playwright harness described in memory already exists; promoting two happy-path specs (instant book + request-to-book) into e2e/ would let the decompositions in ARCH-06/07 be done safely. ### DATA — Data layer, schema & queries (grade B)

The data layer is unusually disciplined for a marketplace at this stage: money is whole-SAR integers everywhere, commission/policy/VAT/invoice values are snapshotted onto bookings, payment and wallet ledgers are append-only with CHECK constraints, capacity and wallet races are closed with FOR UPDATE and advisory xact locks, and every partial index in db/schema.ts is annotated with the predicate it serves. Public reads go through boundedQuery with a pool-reset retry and degrade to empty/sample data, and analytics writes are isolated on their own one-connection pool. The main structural failure is provenance: the Drizzle migration history stopped at 0031 (2026-08-02) while eight tables and eleven bookings columns were added via ad-hoc supabase/*.sql and MCP, two admin tables have DDL only inside markdown, and the RLS-enable step is recorded nowhere in the repo — so the schema cannot be reproduced from the repository and drizzle-kit is now a destructive tool. Secondary issues are a seed script that deletes catalog tables with no environment guard (against a DATABASE_URL that in this project points at the live DB), payment-ledger rows written outside the transactions whose state changes they record, admin list filters applied in memory after a LIMIT while dashboard tiles count in SQL, and a ~95-column bookings table that list queries hydrate whole (encrypted refund IBANs included). None of these is a live outage, but the migration drift is the kind of problem that blocks safe change and gets worse every week it is left.

**Strengths noted by the reviewer:**

- Money is stored as whole-SAR integers with basis-point rates everywhere (db/schema.ts: priceSar, totalAmount, commissionBps, vatRateBps, walletAppliedSar); SQL money math in features/bookings/lib/payout-sql.ts is the single shared definition mirrored by the unit-tested splitCommission, and the uncommitted collectedRevenue() removes a third transcription of GMV.
- Snapshot discipline: commissionBps, the cancellation-policy tier parameters, VAT rate/registration and invoice line items are copied onto each booking at the relevant moment, so editing an experience, a tier, or the VAT toggle never restates existing rights or issued documents.
- Append-only ledgers (payment_events, wallet_ledger, payout_clawbacks, *_events audit tables) with real CHECK constraints (wallet_ledger_amount_nonzero, payout_clawbacks_amount_positive, reviews_rating_range) and a partial unique index closing the one-open-dispute race.
- Concurrency is handled at the right layer: booking creation, approval and reschedule lock the experience row FOR UPDATE before re-summing capacity (features/bookings/actions.ts:790-806); wallet debits serialize on a per-guest pg_advisory_xact_lock with a documented lock order; settle and refund use conditional UPDATE ... RETURNING as the arbiter.
- Indexes match the predicates actually used and each is commented with the query it serves, including partial indexes for nullable hot columns (bookings_payment_deadline_idx, bookings_created_ip_created_at_idx, user_roles_user_idx WHERE revoked_at IS NULL).
- Resilience under DB trouble is engineered, not hoped for: lib/deadline.ts boundedQuery converts poisoned-pooler hangs into a bounded retry on a fresh pool (lib/db.ts resetDb with generation guard), public queries degrade to empty/sample data, and fire-and-forget analytics writes run on an isolated max:1 pool so they cannot poison the shared one.
- Timezone handling is pinned to Asia/Riyadh at the formatting layer (lib/format.ts) and to a fixed +03:00 offset for instant construction, which is exact for KSA (no DST).
- RLS posture is explicit and consistent: RLS on, no policies (deny-by-default via PostgREST), app connects as a BYPASSRLS role, and the newer ad-hoc DDL files repeat the enable-RLS step.

(L/medium)

### MONEY — Bookings, payments, wallet & payouts (grade B)

The money core is unusually disciplined for a small team: every amount is a whole-SAR integer computed server-side (priceSar × partySize), settlement is idempotent behind a conditional UPDATE that re-asserts the amounts it compared, refunds claim refundDueSar before any gateway call and journal refund_attempted/succeeded/failed around it, wallet credit is debited at apply time under a booking row lock plus a per-guest advisory lock, and payout math is single-sourced in splitCommission/payoutExpr with snapshots on the booking. Nine prior audit rounds show in the code and I found no P0 or P1: no unauthenticated mutating money action, no client-trusted amount, no double-spend path in wallet or promo, and every crash window between a status flip and its money leg has a cron sweep or alert behind it. What remains is race-class hygiene and policy drift: the guest/host/admin cancel flips do not re-assert paymentStatus (a settle landing mid-cancel yields cancelled+paid with no refund and a wrong email until Pass 1c alerts), createCheckout's compare-and-swap does not re-assert that the hold is still live, the OPPWA webhook discards the checkout id so a capture on a superseded checkout can stay invisible, and the 2026-08-21 bank-transfer toggle turned the wallet 'refund to card' exception into a bank transfer while the guest cancel form now hard-requires an IBAN regardless of the toggle. The latent structural issue is precision: VAT is rounded to whole riyals, which will not survive ZATCA registration. The uncommitted diffs (slot-clock gate on confirm and createCheckout, collectedRevenue(), suspension guest notice, watchdog cron) are correct and tested; none introduces a new money defect.

**Strengths noted by the reviewer:**

- Whole-SAR integer money model with zero client-provided amounts: totalAmount = experience.priceSar × partySize on the server (features/bookings/actions.ts:731), markHostPaid treats the posted expectedAmountSar purely as a CAS guard (features/admin/payouts/actions.ts:134), and settle rejects any capture that is not exactly the prepared amount (features/payments/settle.ts).
- Settlement is a genuine idempotent arbiter: the paid UPDATE re-asserts paymentStatus<>paid, totalAmount and walletAppliedSar, losers re-read and return already_settled or a permanent, deduped anomaly; the VAT snapshot uses a strict settings read so an outage leaves the row processing rather than under-declaring tax.
- Refund executor discipline: claim refundDueSar before money moves, refund_attempted written before the gateway call, EXCEPTION terminal event on throw, refundInFlight/refundOutcomeUnknown guards in the admin action, card-first split with an idempotent refund:<bookingId> wallet key, and least()-capped accumulation of refundedAmountSar.
- Wallet ledger is append-only with debit-at-apply under booking FOR UPDATE + pg_advisory_xact_lock, in-transaction reservation release on every unpaid kill, a lifetime source cap on refund-out, and an expiry sweep that protects refund_credit — the non-withdrawable model is actually enforced, not just documented.
- Payout correctness: commission/VAT/discount/credit snapshots live on the booking, splitCommission and payoutExpr are mirrored and unit-tested, owed rows are locked FOR UPDATE inside the batch, clawbacks are unique per booking and planned greedily by the same function the page displays.
- Operational nets for every known crash window: stranded-reservation sweep (1b), orphaned-refund watch (1c), refund-out orphan sweep (1d), reconcile blind-spot alert (2c), negative-take and VAT-threshold tripwires, heartbeat plus a separate watchdog cron — all bounded per run and idempotent at any cadence.
- Test coverage on the money core is real: settle, refund, refund-split, transition-executor, reservation, checkout-actions, policy and commission each have dedicated suites, and the uncommitted work adds tests pinning the new slot-clock gate and the collectedRevenue() SQL.

**Development areas proposed by this reviewer** (folded into §6):

- *Halala-precision money model before ZATCA registration* — All money is integer SAR. VAT, tax invoices and credit notes need 2-decimal amounts to reconcile; deciding the storage/rounding model (halala integers vs numeric) before the first VAT-stamped booking avoids a restatement of history the code explicitly promises never to do. (L/high, brief)
- *Daily gateway settlement-report reconciliation* — The cron comments name captures on superseded checkouts as a gap that only HyperPay's settlement report can close. A daily job that pulls the report (or the OPPWA reporting API) and diffs it against payment_events settle_succeeded/refund_succeeded rows would make every SAR at the gateway accountable in the ledger. (M/high)
- *Host share of forfeited late-cancellation revenue* — Payouts accrue only on status='completed'; a guest's forfeited or 50%-withheld payment is 100% platform revenue (forfeitedSar) and the host who held the date gets nothing. Marketplaces normally pay the host their share of retained cancellation money. This is an owner decision that then needs payout-sql and clawback changes. (M/high)
- *Payout execution automation* — Payouts are a manual 'Mark paid' after an off-platform bank transfer, and memory notes SAR 3,770 has sat unpaid. A bank-file export or SADAD/bank API integration with the same batch record would remove the human bottleneck the hosts feel first. (M/medium, brief)
- *Decompose the release-holds cron into per-pass modules* — app/api/cron/release-holds/route.ts is 1,130 lines and 15 passes in one try block; one thrown pass (before the per-pass try/catch ones) aborts the heartbeat and everything after it. Per-pass modules with their own error isolation, timing metrics and unit tests would make the platform's heartbeat safer to change. (M/medium)
- *Interleaving tests against a real Postgres* — The money invariants are enforced by conditional UPDATEs and advisory locks whose correctness depends on real SQL semantics; today they are pinned by mocked-db unit tests. A CI job running settle×cancel, apply×settle and refund×refund interleavings against a throwaway Postgres (or Supabase branch) would catch MONEY-01/02-class races mechanically. (M/medium)

### SEC — Security & authorization (grade A)

Authorization is consistently enforced at the right layer: every one of the ~40 server-action files re-derives the actor from the session (never from the form), admin writes and both PII exports go through the single requireAdminActor() gate that combines the user_roles lookup with an in-app TOTP second factor, host writes scope every read and conditional UPDATE by hosts.userId, and guest-side booking mutations use one greppable access model (signed-in owner, signed last-booking cookie, or — for pay-in actions only — the signed ?k= link token). All three webhooks verify authenticity (AES-GCM tag, Twilio HMAC-SHA1, Svix HMAC-SHA256 with replay window) with constant-time compares, the cron routes require a Bearer CRON_SECRET that lives in Supabase Vault rather than in the committed SQL, open redirects are neutralised by sanitizeNextPath, OTP send/verify and TOTP verification are DB-throttled per identifier and IP, host IBANs/IDs and guest refund IBANs are AES-256-GCM encrypted at rest, and no secret is committed anywhere in the tree. The remaining weaknesses are hardening items rather than holes: Sentry scrubbing misses request URLs (so non-expiring booking link tokens can reach the monitoring tool), the pay-return route still acts as a time-bounded token oracle for anyone holding a bare reference UUID while a booking sits in processing, the admin MFA marker survives sign-out, the payment return-URL origin can fall back to a request header, upload MIME types are trusted from the client, and the env-based admin allowlist silently overrides a revoked user_roles grant. Nothing found is exploitable today without an additional secret or a leaked identifier.

**Strengths noted by the reviewer:**

- One admin gate for reads, writes and route handlers: requireAdminActor() (features/admin/guard.ts) checks role + completed TOTP + DB, and every admin action file, both CSV exports, and the /admin/dev preview use it — the 2026-08-21 drift (rendering gated, actions not) cannot recur without bypassing the shared helper.
- Booking access model is explicit and greppable: bookingViewerCanAccess (owner or signed cookie) for anything that moves money out or changes contact details; checkoutViewerCanAccess (adds the ?k= token) only for pay-in actions; refund-bank details, cancel, reschedule, contact edits and wallet actions all refuse the token, with comments stating why.
- Cookies that grant access are HMAC-signed with domain-separated keys (last-booking cookie, admin MFA marker, link token, unsubscribe token), verified in constant time, and fail CLOSED in production when no signing key is configured.
- Webhook authenticity is done correctly on all three inbound channels (HyperPay AES-256-GCM tag, Twilio HMAC-SHA1 over URL+sorted params, Resend/Svix HMAC-SHA256 with 5-minute timestamp tolerance), and settlement never trusts the webhook or browser redirect — settleBooking re-queries HyperPay.
- Identity-linking rules are sound: an unverified form phone never binds a guest row to an account; claiming an anonymous row requires evidence; the WhatsApp support agent gates every write tool behind a server-enforced identity challenge with its own throttle bucket, and tool availability is computed server-side (toolsFor) rather than trusted from the model.
- OTP abuse controls exist at three layers (30s cookie cooldown, DB throttle per identifier and per IP for sends and failed verifies, Supabase provider limits), and admin TOTP verification adds a replay guard (last_used_step) plus the same throttle.
- Secrets hygiene: only .env.example is tracked, the pg_cron jobs read CRON_SECRET from Supabase Vault, serverEnv is server-only and the client bundle only ever sees NEXT_PUBLIC_* values, stub auth is impossible under NODE_ENV=production.
- PII at rest: host national IDs / CR numbers / payout IBANs, guest refund IBANs and admin TOTP secrets all pass through encryptPii; admin CSV exports defuse formula injection; JSON-LD escapes <, >, & to prevent stored XSS via host-authored copy.

**Development areas proposed by this reviewer** (folded into §6):

- *Ship a real Content-Security-Policy (nonce-based script-src, restricted connect-src) beyond frame-ancestors* — Deferral is deliberate and recorded, but the app now hosts a card widget, third-party pixels (GA4/TikTok/Snap) and Leaflet tiles; an XSS anywhere would run with access to the booking cookie surface. Start with report-only mode to learn the OPPWA/pixel origins, then enforce. (M/high)
- *Verify and pin Supabase Storage bucket policies in-repo (kyc-documents private, photos/avatars write-denied to anon), with a CI check* — Authorization for storage lives entirely in server actions over a service-role key; the bucket policies are the only independent backstop and the 2026-08-02 audit left 'kyc bucket policy' open. Record the policies as SQL in supabase/ and assert them in CI via the Supabase API. (S/medium)
- *Short-lived, purpose-scoped link tokens (expiry + scope in the signed payload) with a v2 label and a migration window* — The current ?k= token is permanent and grants read + pay. Adding exp/scope fields (e.g. receipt-only forever, pay-only for the hold window) would shrink the blast radius of a forwarded WhatsApp message and close the pay-return oracle cleanly. (M/medium)
- *Security regression tests for authorization invariants* — guard.test.ts pins the admin gate, but there is no structural test that every 'use server' file under features/admin imports requireAdminActor, that every host action scopes by hostId, or that no action accepts the link token outside the checkout family. A small AST/grep-based vitest would freeze the invariants the audits keep re-verifying by hand. (S/medium)

Money-moving actions (refundBooking, markHostPaid, issueWalletCredit) warrant a fresh code, and the audit trail is split across hostStatusEvents/userProfileEvents/paymentEvents. (M/medium)
- *Dependency and supply-chain guardrails (lockfile-only installs, Renovate/Dependabot, pnpm audit already in CI)* — CI runs `pnpm audit --prod --audit-level=high`, which is good; adding automated update PRs and `--frozen-lockfile` enforcement keeps the payment and auth dependencies (postgres, @supabase/ssr, twilio) current without manual sweeps. (S/low)

### AI — WhatsApp support agent (grade B)

The WhatsApp support agent is unusually well-architected for a small team: identity is never a model parameter (every tool is bound to the conversation's sender resolved from the phone before the model runs), the three booking-changing tools are gated twice (withheld from the tool list AND refused in runTool) behind an email challenge whose results deliberately never echo the stored address, confirmations must literally appear in the guest's latest short message, the loop is capped at 6 iterations, thinking blocks are round-tripped correctly, the model id and SDK surface (claude-opus-4-8, adaptive thinking, output_config.effort, 1h ephemeral cache on a frozen prefix) are correct for @anthropic-ai/sdk 0.120.0, and every failure path degrades to ack + ticket + human handoff rather than silence. The real weaknesses are operational rather than exploitable: a second WhatsApp message arriving while a turn is running is silently dropped and never swept (the code comments describe a re-check that does not exist), there is no per-number or global spend/alert ceiling so a stranger can burn Opus tokens and page the admin's WhatsApp at will, the email verification never expires and the conversation→guest binding is sticky for the 12-month retention window, and the audit trail cannot distinguish an agent-driven cancellation or IBAN change from a web one even though the manual bank transfer is explicitly the 'human in the loop' that the identity design relies on. Plaintext IBANs sit in conversation_messages while the same IBAN is encrypted on bookings. Test coverage pins the authorization boundary (good) but not the DB half of the challenge, the lock, or the fail-safe.

**Strengths noted by the reviewer:**

- Tools carry no identity parameters (tools.ts:31-36, pinned by tools.test.ts:52-57); the sender is resolved from the WhatsApp number before the model runs, so no prompt can redirect a lookup to another guest.

- Correct SDK usage for the current API: default model claude-opus-4-8 (env.ts:136), thinking {type:'adaptive'} + output_config.effort, frozen rules+knowledge in the first system block with cache_control ttl 1h and the volatile per-conversation block after it (agent.ts:137-152; prompt.ts:1-6), full response.content pushed back so thinking blocks survive tool loops (agent.ts:173), refusal stop_reason handled (agent.ts:155).

### ACTIONS — Server actions & forms (grade B)

The server-action layer is unusually disciplined for a codebase this size: all 40 action modules open with 'use server', every one I read validates with a shared zod schema via safeParse, returns a discriminated failure code (never a raw throw — grep found zero throws that reach the client other than redirect()), echoes `values` on text-input forms, and routes admin writes through one TOTP-enforcing guard. ### REACT — React / Next.js rendering (grade B)
